# 21 · TP 历史时间归属与 v4 计量

2026-09-15。M3 的专门数值/时间复核。原始 EBU WAV 素材验收状态不变。

## 已复现的问题

v3 使用 libebur128 的 previous-block TP 值，直接贴到同一个输入块的 10 ms 索引。库里的 FIR 插值器带群延迟，该接口又与当前 sample peak 取最大值，导致一个值混合了两个时间范围。

独立零相位卷积参考的初始 64 个组合全部暴露问题。例如 48 kHz 的第一窗实际应为 1.082030（约 +0.685 dBTP），旧窗口只有 0.8（约 −1.938 dBTP）；峰值被延后到另一个窗口。100 ms 前的前缀 Max TP 也未及时建立。

失败记录：.tools/m3-tp-time-before.log。没有通过放宽数值容差解决。

## 当前规则

配置 ID：trace-meter-v4-ebur128-1.2.6-lra10hz-tpaligned。

- 继续使用同一个 libebur128 插值器，没有另写产品 TP 算法。
- 49-tap FIR 群延迟为 24 个插值输出样本：低于 96 kHz 时 4 倍插值，需 6 个源帧；96 kHz 时 2 倍插值，需 12 个源帧。
- 按补偿后的源位置归入 10 ms 窗口，窗口是 [floor(k*rate/100), floor((k+1)*rate/100))。
- 首部负时间滤波响应归入第一窗，真实 EOF 之后的尾响归入最后一窗；属于明确的零延拓边界处理，不增加录音帧数。
- 同窗 TP 至少包含同窗的真实 sample peak，同时包含插值峰值；不能把当前输入块的 sample peak 与另一个时间窗的 TP 混合。
- 收到必要 lookahead 后才发布完整窗口。Peak/RMS/TP 使用同一已发布索引；M/S/I/LRA 保留各自 100 ms 索引。
- 待发布帧队列最多 3 项，TP 临时槽固定 4 项；输入尾块及时送入引擎。发布滞后不超过 ceil(rate/100)+lookahead 帧，停止时排空为 0。
- N-API diagnostics 新增 truePeakLookaheadFrames 和 meterLagFrames。它们是分析诊断，不是回放设备延迟。
- 录音 PCM 仍直接进独立写盘队列，不等待对齐后的显示/计量快照。

## 实现边界

第三方库增加一个可选的原生观察接口，提供已存在的插值输出及位置；默认不启用，原有标量 API 保留。该 C 回调只做固定内存运算，不做 JS/磁盘/锁等待。修改链及 SHA256 在 SOURCE.json，许可保留。

Meter::setFrameSink 在分析所有者线程提供每一个完整帧。FileAnalysis 和 Recorder 通过它接收全部窗口；finish 可能发布不止一条记录，不能只读取 latest 值，否则会丢掉部分 EOF 前的窗口。

v3 的 10 Hz LRA 与 1.5 秒 EOF 分析上下文继续保留。M/S/I/RMS/Peak 的真实 EOF 值和真实帧总数不随上下文增加。

## 并行初始化修正

审查发现库在每次构造时重写共享常量/直方图查找表，可能与另一实例的读取并发。现在由 EburConstants.cpp 使用 call_once 初始化一次，然后只读；数值公式原样保留。

独立进程中的 8 个线程在四种采样率下创建/运行/销毁 32 个 Meter，确认所有读数有效且初始化计数恰为 1。该修正不在音频采集回调中引入锁。
